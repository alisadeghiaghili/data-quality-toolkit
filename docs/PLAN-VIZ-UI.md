### 1.1 One defect to fix before anything is built on it

`src/dqt/ui/app.py`'s module docstring shows the app being served with:

```python
uvicorn.run(app, host="0.0.0.0", port=8000)
```

That binds every interface. The app has **no authentication of any kind**, and
what it serves is schema names, table names, column names and issue messages
read out of a production database. Read-only does not mean harmless: a schema
listing is reconnaissance.

The example must be `127.0.0.1`, with the reason stated. Anything beyond
localhost is a deployment decision that needs authentication first, and DQT
should not hand out a one-liner that skips it.

## 2. The stack decision

### 2.1 What was rejected, and why

**A React/Vue single-page app.** It would mean a Node toolchain, a bundler, a
lockfile, a build step in CI, and a compiled asset bundle shipped inside a Python
wheel — a second language ecosystem to hold to the same standard as the first.
For a fixed set of opinionated read-only screens that is a large permanent cost
buying interactivity DQT's screens do not need. `docs/DQT-UI-Ecosystem.md`
already names configurable dashboards as an anti-pattern; an SPA is the shape
that invites them.

**matplotlib (or any plotting library).** DQT needs bar charts, trend lines,
scorecards and severity indicators. A plotting library would add a heavy
dependency with binary wheels, emit a **raster** image that cannot be styled by
the page or read by a screen reader, need its own font configuration for
Persian, and — the decisive point — **produce output no test can assert.** A PNG
can only be smoke-tested: "it did not crash". This project's honesty gate says a
claim needs a passing test behind it, and "the bar for `validity` is drawn
shorter than the bar for `completeness`" is a claim.

**HTMX as a foundation.** It is one small file with no build step and it is a
reasonable tool, but plain server-rendered pages with querystring filters get a
fixed-screen DBA dashboard almost all the way there — and they are keyboard
accessible and back-button correct *by construction* rather than by discipline.
HTMX stays available as a per-screen enhancement if one screen proves it needs
partial updates; it is not the base.

### 2.2 What was chosen

**Charts: inline SVG, generated by pure Python functions in `viz.py`.**
No plotting library, no JavaScript, no image files.

- The output is a deterministic string, so a test can assert the geometry: this
  bar is this many pixels because the score is 0.62.
- It scales crisply, inherits the page's CSS (including dark mode and RTL), and
  survives being emailed inside a single HTML file.
- Every chart function returns the SVG **and** its text equivalent, so the
  accessibility requirement is structural rather than remembered.
- Zero new runtime dependencies.

**Templates: an escape-by-default builder, shared by both delivery modes.**
`reports.py` escapes correctly, but through twenty-odd separate `html.escape`
calls — correctness by per-line discipline, where one omission is silent.

> **Reversed 2026-09-05, during `VIZ-2`.** This section first said Jinja2.
> `docs/BACKLOG.md` §4 rules out new **hard** dependencies, and the Reports
> facet has to work with no extras installed — so Jinja2 would either become
> DQT's fourth required dependency or force two renderers, and two renderers
> is the one thing this plan exists to avoid.
>
> `dqt/_html.py` is the same property without the dependency: one rule, *text
> is escaped, markup is explicit*, and it costs about as much code as the
> `html.escape` calls it replaces. The plan's actual requirement — one
> renderer for both delivery modes — is unchanged.

**Pages: server-rendered by the existing FastAPI app.** No new service, no new
process model.

### 2.3 The idea the whole plan turns on

**One renderer, two delivery modes.**

```
        dqt.ui.api  (read-only dicts over RunStore)
                 │
                 ▼
        viz.py  →  SVG + text equivalent          templates/  (Jinja2)
                 └──────────────┬──────────────────────┘
                                │
             ┌──────────────────┴──────────────────┐
             ▼                                     ▼
   static self-contained .html              FastAPI pages
   (email it, attach it to a ticket,        (browse, filter,
    archive it — no server)                  drill down)
```

The same templates and the same chart primitives produce both. The static report
gets every chart the dashboard has, for free, and there is one place where a
severity colour or a score badge is decided.

This also settles a tension in `docs/DQT-UI-Ecosystem.md`, which concluded that
the shareable static artifact (the Great Expectations Data Docs pattern) is often
worth more to a DBA than a server — and then listed a full dashboard as the
target. Both, from one renderer, is the answer to that.

## 3. Screen inventory

Every screen names its facet. A screen that cannot name one does not ship.

| # | Screen | Facets | Delivery |
|---|---|---|---|
| 1 | **Overview** — run header and status badge, six dimension scorecards, issue counts by severity and dimension, score trend | Metrics, Diagnostics, Monitoring | both |
| 2 | **Explorer** — schema/table list; per-table completeness, row count, issues by severity, last check | Profiling, Metrics | both |
| 3 | **Column & Issue detail** — column stats, semantic type, rules targeting it; filterable issue list with evidence | Profiling, Classification, Rules, Diagnostics | both |
| 4 | **Rules** — definitions, scope, last result, and rules matching **zero targets** | Rules | dashboard only (see §6) |
| 5 | **Report export** — the static artifact, with its scope and time window stated inside it | Viz/UI, Reports | static |
| 6 | **Missingness panel** — shown only when `external_analyses["missingly"]` is present | Missingness, Imputation | both |

Navigation is a single spine with breadcrumbs, no dead ends:

```
Overview  →  schema  →  table  →  column  →  issue
   └────────────────── Rules ──────────────────┘
```

**The run status badge is not decoration.** A `partial` or `failed` run must be
impossible to mistake for a healthy one, with `stage_errors` reachable from it.
A dashboard that renders a failed run green is worse than no dashboard — it is
the same defect Phase 0 existed to remove, wearing a nicer font.

### 3.1 Counts come from the canonical lists

Every count, score and chart is derived from the flat `PipelineResult.issues` /
`.metrics` lists filtered by scope — never by summing the nested per-table or
per-column collections, which are navigation views and double-count. This is
`CONVENTIONS-DQT-data-model.md` §0, and it is the single most likely way for a
dashboard to be confidently wrong.

## 4. Accessibility

Not a polish pass. These are acceptance criteria for every unit below.

- **Severity is encoded by colour *and* an icon *and* a text label.** About 8% of
  men have some colour-vision deficiency, and DBAs stare at these tables all day.
  A red/amber/green-only scheme is unreadable to a meaningful slice of the exact
  audience.
- Contrast at WCAG 2.1 AA: 4.5:1 body text, 3:1 large text and UI boundaries.
- Every chart ships its text equivalent — `viz.py` returns it alongside the SVG,
  so it cannot be forgotten.
- Full keyboard path, visible focus, nothing reachable by hover alone. Plain
  server-rendered pages give most of this for free, which is part of why they
  were chosen.

## 5. Bilingual EN/FA and RTL

Report and UI text are bilingual. **CLI output and code stay English-only** —
that is unchanged.

- `dir="rtl"` at the container, with per-block direction so identifiers, SQL and
  numbers stay LTR inside RTL text.
- Mirror the layout, not the data: navigation and reading order flip; charts,
  timelines and code blocks do not.
- **Vazirmatn** (SIL OFL), subset and base64-embedded in the static report so it
  stays self-contained. Persian rendered without proper Arabic-script shaping is
  not slightly off, it is unreadable. The licence text ships with the font.
- A fixed EN↔FA glossary for the six dimension names, maintained beside the
  reports module. A dimension name translated two ways in one report is a
  correctness bug, not a style issue.

## 7. Blockers, named rather than designed around

These are places where the UI specification assumes data DQT does not have.
Building a screen over an absence produces a screen that lies.

1. ~~**No `run_rule_results` table.**~~ **Cleared by `NEW-S`** (2026-09-05).
   The table exists, `save_run` writes it — it was silently dropping
   `PipelineResult.rules_run` on every run — and `RunStore.load_rule_results` /
   `load_rule_history` read it back, reachable through `dqt.ui.api`. Existing
   store files must be deleted and recreated; the schema version guard refuses
   them by name rather than half-using them.

2. ~~**No `dqt_version` on `runs`.**~~ **Cleared by `NEW-S`.** The pipeline
   stamps the running version onto the result and the store records it. A
   result that does not state one is stored as unknown rather than guessed
   from whatever is installed at save time.

3. **There is no evidence sample to suppress.** The UI spec describes an
   `EvidenceConfig` and a "samples suppressed by configuration" state. Neither
   exists, and that is deliberate: `DQIssue.evidence` carries **counts, never
   rows**, and `tests/unit/sql/test_rules_cost.py` pins it, so a report's size
   never depends on how bad the data is. The evidence panel shows counts. No
   placeholder implying a missing feature.

4. **The dashboard stays strictly read-only in this plan.** The UI skill permits
   a "run checks on selected tables" action. Given §1.1 — an unauthenticated
   HTTP surface — a button that opens a connection to a production database is
   not something to add before authentication exists. Runs are launched by the
   CLI. Cleansing `apply` is not in the UI at all, in any version: that is
   locked decision `Q1`, and it is structural, not a flag.

5. **The `dqt-ui-designer` skill's dialect list is stale.** It says SQLite and
   PostgreSQL only. SQL Server landed in `DQT-08` and is exercised against a live
   instance in CI. Any screen reflecting a connection type must show three.

## 8. Explicitly cut

Kept here so the decisions do not get relitigated:

- Widget builders, configurable dashboard layouts, cross-filtering engines,
  dashboard parameters, ad-hoc chart construction, a query or pivot surface.
  Every step toward configurability is a step toward being an unfinished BI tool.
- Masking, compliance, MDM screens — permanent non-goals.
- Any service-quality chart: latency, CPU, uptime, wait stats. "Monitoring" in
  DQT means data-quality metrics over time, and the shared vocabulary must not
  be allowed to pull service metrics in.
- ML training or labeling surfaces. DQT has no ML and does not need one.
