# DQT — The Honesty Gate, Made Concrete

> **Normative, and ranked above `docs/CONVENTIONS-DQT.md`.** This document is
> DQT's concrete implementation of the ecosystem's honesty gate
> (`ROADMAP.md` §2.4). It does not restate that gate's rationale — read §2.4 for
> why it exists — it answers the question that section leaves open for each
> repo: **what counts as external ground truth here, specifically, in a SQL
> data-quality tool that has no R oracle and no published statistical
> reference?**
>
> If a claim in any other document in this set contradicts this one on what
> counts as evidence, this document wins.

---

## 0. The rule, stated once

**A claim that code works is not evidence that code works. Running that same
code again and checking it agrees with itself is not evidence either.**

Evidence is something that would still be true if every line of DQT's own test
suite were deleted and rewritten by someone else. Four shapes qualify:

1. **A checksum or hash comparison** of state before and after an operation —
   proves *what changed*, not just *that something ran*.
2. **An independent reproduction of the defect**, written by someone other than
   the person fixing it, executed against both the broken and the fixed code.
3. **A seeded fixture with a known, hand-computed expected value** — not a value
   the code itself produced and the test merely echoes back.
4. **A property-based invariant** that holds regardless of implementation —
   round-trip identity, idempotence, a conservation law (row counts before an
   operation equal row counts after, for an operation that must not lose rows).

A fifth thing is explicitly **not** on this list and is the mistake this
document exists to prevent: **a unit test that calls the function and asserts
the result equals whatever the function returned when the author last ran it.**
That is not a test of correctness. It is a test that the code has not changed
since the test was written — which is a real property, but a much smaller one,
and it is the property that produced this repository's eleven false `[x] DONE`
markers.

## 1. What this looks like for DQT specifically

DQT has no R oracle (`missingly` does — see `VERIFICATION-LOG.md` for what that
looks like in practice). Its ground truth has to come from elsewhere. In order
of preference for this codebase:

| Situation | Ground truth to use |
|---|---|
| A SQL-injection or identifier-quoting fix | An exploit string written before the fix exists, that succeeds against the broken code and fails against the fixed code. Write the attack first; if you cannot make it succeed against `main` before you start, you have not reproduced the defect. |
| A read-only / write-prevention guarantee | A four-hash checksum: hash the database file before the run, after a read-only run, after an attempted write under the guard, and after a real write with the guard removed. The guarded and unguarded-before states must match; the unguarded-after state must differ. This is exactly the proof `DQT-03` already produced — reuse its shape. |
| A cleansing / revert round-trip | Checksum the affected rows before mutation, after mutation, and after `revert()`. Before and after-revert must be byte-identical. Additionally: kill the process between the mutation and the log write, and assert nothing committed — a log that can be lost mid-transaction is not an audit trail (`CONVENTIONS-DQT.md` §1, S4). |
| A profiling or metrics calculation | A fixture database with hand-computed expected values (null ratio, distinct count) computed independently of the code under test — by hand, by a spreadsheet, or by a one-line SQL query run manually and pasted into the test as a comment showing the derivation. |
| A rule engine change | A fixture where the expected pass/fail set is enumerated by a human reading the data, not generated by running the rule and capturing its output. |
| Anything claiming "no new failures" | The *collected* test count, pasted before and after, not just the passed count. A suite that goes from 158 passed to 158 passed after deleting 40 tests and adding 40 unrelated ones is not "no new failures" — see `ROADMAP.md` §3.7. |

If none of these fit a specific claim, say so explicitly in the task report
rather than substituting a self-referential test and calling it done. An honest
`STATUS: BLOCKED` with "I don't have a ground truth for this claim, here is what
one would require" is compliant. A self-referential test presented as proof is
not, regardless of whether it passes.

## 2. The fail → pass proof, mandatory for every bug or security fix

This is not optional and not satisfied by "I added a test and it passes." The
required transcript has four steps, in this order, all pasted:

1. **Revert the fix** — `git stash` it, or check out the pre-fix commit.
2. **Run the new test against the unfixed code. Paste the failure.** If it
   passes against unfixed code, it is not testing the defect.
3. **Restore the fix.**
4. **Run the same test again. Paste the pass.**

This is what makes a fix a fix rather than a coincidence. It is also what
already happened for `DQT-02` (control run against `132ba3e` reproduced the
leak — `out_of_range=3`, exactly the payload arithmetic) and `DQT-03` (control
run against `a1f6ce7` failed 6 of 8 tests, including `DROP TABLE` succeeding on
a connection that was supposed to be read-only). Those two are the reference
examples for what this section requires — not aspirational text, a description
of work already done correctly.

## 3. What currently enforces this, and what does not

Recorded so nobody assumes more automation exists than does.

**Enforced by process, today:**

- The roadmap's mandatory report format (`TASK`, `STATUS`, `VERIFICATION
  COMMANDS + OUTPUT`, `PROOF THE TEST CATCHES THE BUG`, …) — a task report
  missing these fields is incomplete, not done.
- Independent supervisor verification — a second party re-runs the claim
  against the *unfixed* code and confirms the transcript in §2 is real. This is
  what `VERIFICATION-LOG.md` records: not a description of the standard, but a
  log of it being applied, including at least one recorded case where the
  supervisor's own initial check was wrong and was corrected.

**Not yet enforced by tooling, in this repo:**

- `tools/doc_audit.py` — a real, self-passing, ratchet-capable gate — is not
  wired into DQT's CI. That is `DOC-01`. It also checks docstring completeness
  and style, which is adjacent to this gate but not the same thing: a
  docstring can have a perfect `Example` block that is itself a self-referential
  test.
- `claim_audit.py` (`ALL-01`) — scans for high-risk phrases without an evidence
  pointer — is being built against `missingly` first; copying it into DQT is a
  separate, unstarted follow-up PR.
- There is no CI job today that would fail a PR for adding a self-referential
  test. This document's requirements are currently carried entirely by the
  report format and human review, not by a gate that runs automatically.

Until `DOC-01` and the DQT copy of `ALL-01` land, treat this document as
mandatory review criteria, not as something the test suite will catch for you.
